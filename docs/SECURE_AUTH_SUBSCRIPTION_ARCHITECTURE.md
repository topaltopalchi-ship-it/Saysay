# معماری امن حساب کاربری و اشتراک سای‌سای

## تصمیم‌های قطعی محصول
- داده‌های حسابداری (کالا، فاکتور، مشتری، موجودی، چک، دریافت/پرداخت و گزارش‌ها) فقط در IndexedDB روی دستگاه می‌مانند.
- این داده‌ها به API حساب کاربری یا اشتراک ارسال نمی‌شوند.
- سرور فقط اطلاعات لازم برای حساب، نشست‌ها و حق دسترسی اشتراک را نگه می‌دارد.
- PIN فعلی محلی به‌تنهایی احراز هویت حساب کاربری محسوب نمی‌شود و نباید به‌عنوان امنیت اشتراک استفاده شود.
- اشتراک پولی فقط پس از تأیید سمت سرور فعال می‌شود؛ زمان آزمایشی محلی فعلی برای انتشار تجاری قابل اتکا نیست.

## معماری پیشنهادی

### کلاینت Android / Capacitor
- فرم ثبت‌نام و ورود با نام کاربری و رمز عبور.
- ارتباط HTTPS با API.
- access token کوتاه‌عمر و refresh token چرخشی؛ نگهداری توکن حساس فقط در فضای امن بومی دستگاه، نه localStorage.
- نگهداری داده‌های حسابداری در IndexedDB محلی.
- هیچ رمز عبور، کلید خصوصی، کلید سرویس بازار یا راز سرور داخل bundle فرانت‌اند قرار نگیرد.
- هنگام بازشدن برنامه، وضعیت نشست و اشتراک از سرور بررسی شود؛ داده‌های حسابداری برای این کار ارسال نشوند.
- در نصب مجدد/گوشی جدید، اشتراک پس از ورود دوباره بازیابی می‌شود، اما داده‌های مالی فقط از نسخه پشتیبان خود کاربر قابل بازیابی‌اند.

### سرور و پایگاه داده
حداقل جداول:
- users: شناسه، نام کاربری نرمال‌شده و یکتا، هش رمز عبور، زمان ساخت، وضعیت حساب.
- sessions: هش refresh token، شناسه کاربر، زمان انقضا، ابطال و اطلاعات چرخش توکن.
- subscriptions: شناسه کاربر، پلن، وضعیت، زمان شروع/انقضا و منبع خرید.
- store_purchases: فروشگاه، شناسه محصول، شناسه خرید/توکن خرید به‌شکل امن، وضعیت تأیید و کلید idempotency.

رمز عبور باید با الگوریتم اختصاصی هش رمز عبور مانند Argon2id و salt یکتا نگهداری شود؛ هرگز متن خام رمز ذخیره نشود. محدودیت تلاش ورود، پاسخ‌های خطای غیرقابل سوءاستفاده، اعتبارسنجی ورودی، rate limiting و ثبت رویدادهای امنیتی لازم‌اند. رمز و توکن‌ها نباید در لاگ ثبت شوند.

## قرارداد API پیشنهادی
- POST /v1/auth/register — ساخت حساب با نام کاربری و رمز عبور.
- POST /v1/auth/login — بررسی رمز و صدور نشست.
- POST /v1/auth/refresh — چرخش refresh token.
- POST /v1/auth/logout — ابطال نشست فعلی.
- GET /v1/subscription/status — فقط وضعیت اشتراک حساب واردشده؛ هیچ داده مالی محلی ارسال نمی‌شود.
- POST /v1/subscription/store/verify — دریافت شناسه محصول و داده خرید از کلاینت؛ سرور خرید را از مسیر رسمی فروشگاه بررسی می‌کند و فقط پس از تأیید، اشتراک را فعال می‌کند.
- POST /v1/subscription/restore — بررسی خریدهای قابل بازیابی برای حساب واردشده.

تمام endpointهای غیرعمومی باید احراز هویت، اعتبارسنجی و محدودسازی نرخ داشته باشند. فعال‌کردن اشتراک بر اساس پاسخ کلاینت یا صرفاً وجود purchase token ممنوع است؛ تأیید باید از سمت سرویس رسمی بازار انجام شود. درخواست تکراری خرید باید idempotent باشد.

## پرداخت کافه‌بازار
1. محصول اشتراک ماهانه در پنل توسعه‌دهندگان بازار تعریف و شناسه محصول در تنظیمات محیطی ثبت شود.
2. لایه Native Android با SDK/روش پرداخت رسمی و فعلی بازار خرید را انجام دهد.
3. کلاینت نتیجه خرید را به API ارسال کند.
4. سرور اعتبار خرید، محصول، مالکیت/وضعیت و تکراری نبودن آن را با سرویس رسمی بازار بررسی کند.
5. سرور تاریخ انقضا را محاسبه و وضعیت اشتراک را ذخیره کند.
6. برنامه در هر ورود و هنگام بازگشت از خرید، وضعیت سرور را دوباره بخواند.

تا وقتی backend، کلیدهای محیطی، حساب توسعه‌دهنده و تأیید رسمی خرید پیکربندی و آزمایش نشده‌اند، خرید واقعی را آماده یا فعال‌شده اعلام نکنیم.

## بازیابی داده‌های محلی
حساب کاربری اشتراک را بازیابی می‌کند، نه دیتابیس مالی را. برای انتقال دستگاه باید بعداً خروجی پشتیبان رمزگذاری‌شده و فرایند واردکردن آن به‌صورت جداگانه طراحی شود. سرور نباید نسخه‌ای از دیتابیس مالی مشتری دریافت کند.

## موانع قبل از انتشار
- انتخاب و استقرار میزبان backend و پایگاه داده.
- تعیین روش امن تأیید حساب/بازیابی رمز (برای مثال شماره تلفن یا ایمیل تأییدشده).
- تنظیم اسرار فقط در secret manager محیط سرور.
- تکمیل SDK پرداخت بومی بازار و تأیید سمت سرور.
- تست‌های ثبت‌نام، ورود، خروج، انقضا، خرید تکراری، restore، آفلاین و نصب مجدد.
- بررسی نسخه Release و سیاست‌های فعلی کافه‌بازار.
